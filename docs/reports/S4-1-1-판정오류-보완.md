## 오류 원인과 수정 조건

### A. 화해 거부 판정 우선순위

- **원인**: `if after and (sorry or self._won_shown("WON_RECONCILE", shown))` — `sorry` 는 withdraw 를 보고 false 가 되지만, 모델이 성공 대사(「…늦었잖아. 그래도, 왔으니까.」)를 냈으면 `or` 뒤에서 화해가 됨. 유저가 분명히 거부했는데 연인 단계로 오를 수 있었음.
- **수정**: 화해의 문 뒤 메시지(`after > 0`)를 판정한 결과에 `withdraw` 가 있으면 성공 대사·apologize·sincere·기억한 `rift_sorry` 보다 먼저 처리:
  - `rift_sorry = false`(앞 단계에서 이미 지움), `crisis = "rift"` 유지, 6단계 상승 없음, `won_line` 없음.
  - 호감은 깎지 않음 — 판정 `affection_delta` 그대로만 반영.
  - 다음 판정에서 withdraw 없이 apologize·sincere(또는 withdraw 없는 성공 대사)가 오면 기존 조건대로 화해.
- 문이 열리기 전의 withdraw 는 S4-1 그대로(기억한 사과만 지움).
- **판정 지침**(`RIFT_JUDGE_NOTE`·JUDGE_SYSTEM): withdraw = 앞서 한 사과·진심을 명확하게 철회하거나 관계 회복 의사를 명확하게 거부. 단순한 투덜거림·서운함·장난·망설임·추가 설명 요구는 아님. 같은 메시지에 사과와 명확한 거부가 함께 있으면 withdraw.

### B. 핵심 사건 완료 횟수

- **원인**: `scene_msgs += 묶음 메시지 수 - (마지막 답장이 「…」면 1)`. 묶음 중간의 실패 답장은 알 수 없어 정상으로 셈(예: 정상 → 실패 → 정상이 3으로 셈).
- **수정**: `/judge` 선택 필드 `reply_ok`.
  - 모양: bool 배열 또는 null(기본). `last_user` 메시지와 같은 순서·개수.
  - 유효하면 `true` 개수만 `scene_msgs` 에 더함.
  - 「[다음 밤]」 줄: 배열 길이가 「[다음 밤]」을 뺀 메시지 수와 같으면 그대로, 포함한 줄 수와 같으면 그 자리 값을 빼고 셈. 어느 쪽이든 「[다음 밤]」은 세지 않음.
  - 배열이 아니거나, bool 이 아닌 값이 섞였거나, 길이가 다르면 예전 계산(묶음 수 − 마지막 답장이 「…」면 1).
  - 장면이 예약만 된 때(pending_event == scene)는 S4-1 그대로 안 셈.
  - 완료 기준 그대로: `SCENE_REPLIES_DONE = 4`(시작 정상 답장 1 + 이후 정상 답장 3).
- 판정 호출은 그대로(기존 /judge 요청에 필드만 더함). `reply_ok` 는 갈래 장면 셈에만 씀(위기·화해 사건의 「…」 다시 넣기는 S4-1 그대로 last_reply 로 봄).

계산 방식 전후:

| 앱 | 계산 | 한계 |
| --- | --- | --- |
| `reply_ok` 안 보냄(지금 앱·연동 전) | 묶음 메시지 수 − (판정한 마지막 답장이 「…」·「...」면 1) | 묶음 중간의 실패 답장을 구분 못 함 → 실제보다 많이 셀 수 있음(장면이 조금 일찍 끝날 수 있음) |
| `reply_ok` 보냄(연동 뒤) | `true` 개수 | 앱이 실패를 정확히 표시하는 만큼 정확 |

### C. 성공 대사 확인 기준

- **원인**: 성공 판단(`_won_shown`, WON_SHOWN)과 「이미 나왔나」(`_won`, WON_KEYS 짧은 조각 하나)가 달라서, 「이제 내려가자.」처럼 일부만 나와도 「이미 나옴」으로 보고 `won_line` 을 비움 → 성공 대사가 끝내 안 나옴.
- **수정**: `_won()` 도 `_won_shown()` 사용. 장난 「연기아니지」, 다정 「내려가자」+「같이」, 화해 「늦었잖아」+「왔으니까」(공백 무시). 모두 있으면 `won_line = null`, 아니면 `WON_TEASE`·`WON_CARE`·`WON_RECONCILE`(원고 블록 그대로)을 다음 답장 STAGE_UP_6 앞에.
- `WON_KEYS` 는 남김: normalize 가 `won_line` 값(블록 이름)을 검증하는 데 씀.

## 실제 플레이에서 확인할 것

- 판정 모델이 서운함·장난·망설임·투덜거림을 `withdraw` 로 과잉 판정하지 않는지(엇갈림에서 화해가 이유 없이 막히지 않는지). 반대로 분명한 거부를 놓치지 않는지.
- 핵심 사건의 정상 답장 4개 기준이 충분한지. 장면이 원고 마지막 대목 전에 끊긴다면 시작 답장 뒤 4~5개(`SCENE_REPLIES_DONE` 5~6)로 조정 검토.
- 성공 대사(WON_TEASE·WON_CARE·WON_RECONCILE)가 두 번 나오거나 아예 빠지지 않는지.
- 거부(withdraw) 판정 답장에 모델이 이미 화해 대사를 낸 경우, 이야기와 상태(엇갈림 유지)가 어긋나 보이지 않는지.

## 제가 정한 것

1. **withdraw 는 「그 판정」에만 적용**: 문 뒤 판정에 withdraw 가 있으면 그 판정에서는 무엇으로도 화해하지 않음. 다음 판정부터는 기존 조건(apologize·sincere·withdraw 없는 성공 대사)대로. 기억한 사과는 지워졌으므로 새 사과·진심이 필요함.
2. **거부했는데 모델이 화해 대사를 낸 경우**: 상태는 엇갈림 유지(지시 A1). 서버가 대사를 지울 수는 없으므로 changes 에 「성공 대사가 나왔지만 거부 우선」을 남겨 점검 때 보이게 함. 다음 답장에도 RECONCILE_WATCH 가 그대로 들어가 다시 화해할 기회가 있음.
3. **문을 연 답장을 판정하는 차례(after = 0)의 withdraw**: 그 차례에는 원래 화해하지 않으므로 기억한 사과만 지움(S4-1 그대로).
4. **reply_ok 길이**: 「[다음 밤]」을 뺀 메시지 수와 같아도, 포함한 줄 수와 같아도 받음(포함하면 그 자리 값은 버림). 앱이 어느 쪽으로 만들든 맞게.
5. **reply_ok 검증**: bool 만 받음(1·0·null 이 섞이면 배열 전체를 무시하고 예전 계산). 서버 요청 모델은 `Any` 로 받아 모양이 틀려도 API 오류(422)가 나지 않게 함.
6. **reply_ok 가 있으면 last_reply 의 「…」 빼기는 하지 않음**: 배열이 더 정확하므로 배열만 따름.
7. **reply_ok 는 갈래 장면 셈에만**: 위기 소식·화해의 문 「…」 다시 넣기는 사건 답장 하나만 판정하는 때(judge_soon)라 last_reply 로 충분해서 바꾸지 않음.
8. **WON_KEYS**: 지우지 않고 won_line 값 검증용으로 남김(예전 저장 호환).

## 프런트 연동 (S4-1 보고서 대비 달라진 것)

### 새: `/judge` 요청 `reply_ok` (선택)

- 키: `reply_ok`, 값: bool 배열 또는 null(안 보내도 됨).
- 조건: `last_user` 의 메시지(줄)마다, 그 메시지에 대한 서아 답장이 정상으로 나왔으면 `true`, /chat 이 실패했거나 「…」(예비 지문)이었으면 `false`. 같은 순서·같은 개수.
- 「[다음 밤]」 줄은 빼고 만들어도, 넣고 만들어도 됨(서버가 그 자리는 세지 않음).
- 실패한 답장을 판정 묶음에 넣지 않는 앱이라면 정상 답장 메시지만 `last_user` 에 넣고 `reply_ok` 는 모두 `true`(또는 안 보냄)로 보내면 됨. 실패 답장을 새로 판정하라는 뜻이 아님.
- 길이나 모양이 틀리면 서버가 무시하고 예전 방식으로 셈(오류 없음).
- 예:

```json
{
  "char": "seoa",
  "state": { "...": "..." },
  "last_user": "응\n따라갈게\n(팔짱을 낀다)",
  "last_reply": "*표적이 맞은편 가게에서 나온다.* 지금. 웃어. …진짜 애인처럼.",
  "need_summary": false,
  "reply_ok": [true, false, true]
}
```

### 바뀐 동작 (앱이 할 일 없음)

- 엇갈림에서 판정 `flags` 에 `withdraw` 가 오면 그 판정에서는 화해(6단계)가 되지 않음. 서아 답장에 화해 대사가 나왔어도 `state.stage` 5, `state.crisis` "rift", `state.stage_label` 「엇갈림」 그대로 옴. 앱은 state 를 그대로 따르면 됨.
- `won_line` 이 S4-1 보다 조금 더 자주 올 수 있음(성공 대사가 일부만 나왔을 때). 다른 때처럼 state 그대로 돌려보내면 다음 답장 앞에 성공 대사가 들어감.

### 그대로 유지

- 서버가 돌려준 `route` 는 그대로 저장하고 바꾸지 않음.
- `scene_msgs`·`rift_sorry`·`stage_note_queue` 는 받은 그대로 돌려보냄.
- `stage_note_queue` 는 `stage_note_due` 와 함께 초기화·되감기(state 통째로)·본편/크리스마스 분리(본편 값 보관만) 처리.
- `stage_note_due` 가 있으면 need_summary 와 상관없이 `recent` 80개 보냄.
- /chat 이 성공해 답장을 보여 준 뒤에만 `pending_event` 비우기, `last_reply` 는 마지막 답장 그대로(「…」 포함).
